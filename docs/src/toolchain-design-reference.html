Requirements · Design Choices · Program Structure — November 2026

This document describes the design, requirements and program structure of the tools that convert Kaikki (Wiktionary) and StarDict dictionaries into PocketBook's native .dic (SDIC) format and into StarDict files for KOReader. Each tool is one Java 25 source file in java/, run without a compilation step through a thin bash wrapper in linux/; what the tools have in common lives in java/shared/.

Usage details (every option, with examples) are printed by each tool with -h; the README and pocketbook-dict-guide.html explain how to build a dictionary step by step; docs/architecture.html shows the structure in diagrams; docs/sdic_format.pdf describes the binary .dic format.

Pipeline

Kaikki .jsonl[.gz]        ── kaikki-2-tab ───┐
                                             ├──► TSV ── tab-2-xdxf ──► XDXF
StarDict .ifo .idx .dict  ── stardict-2-tab ─┘

XDXF        ── xdxf-2-pbdic ─────► .dic        (PocketBook)
XDXF        ── xdxf-2-stardict ──► stardict.*  (KOReader)
XDXF + .dic ── check-pbdic ──────► report      (testing)

Every source becomes TSV (word⇥definition, definitions in HTML), and TSV becomes XDXF, so a new source only needs a new *-2-tab converter, and every back end reads the same XDXF.

Runtime

JavaJDK 25 or later, java on the PATH (source-file mode: no build step, no external libraries)
Launchlinux/<tool> calls linux/runjava <Class>.java, which runs java --source 25 java/<Class>.java; it finds java/ relative to itself, so the tools run from any folder
Sourcesjava/Conv*.java, java/CheckPbdic.java (one class per tool) and java/shared/*.java

Command line and config files

  • Options have a short and a long form (-i / --in); - as a file name is stdin or stdout where the help says so; -h / --help prints the usage to stdout and exits 0.
  • Config file (-c / --config): a .properties file; each tool reads only the keys of its own namespace (kaikki2tab.*, stardict2tab.*, tab2xdxf.*, xdxf2pbdic.*, xdxf2stardict.*, checkpbdic.*), so one file can drive several tools. Command-line options override it. Unknown keys of the tool's namespace are reported.
  • Variables: def <name>=<value> lines define variables used as $name or ${name} ($$ is a literal $); --def <name>=<value> sets or overrides one from the command line (repeatable).
  • Configuration listing: before working, each tool lists the values it uses and where each came from (command line, config, default) on stderr.
  • Typed values are checked when read: languages are ISO 639-1 codes, booleans are true/false, enums (-m, -e) accept their names in any case; the listing shows the normalised value.
# confs/kaikki2xdxf-pt-pt.config (excerpt)
def version=2026-11
def lang=pt
kaikki2tab.in=data/kaikki/kaikki.org-all-to-Portuguese.jsonl.gz
kaikki2tab.out=-
kaikki2tab.lang=$lang
tab2xdxf.in=-
tab2xdxf.out=data/out/kaikki-pt-pt-${version}.xdxf

Output: all or nothing

Every converter writes through IoHelper.SafeOutput: the output is kept in memory, compressed (about 1/8 of its size for dictionary text), and reaches the file or stdout only on commit(), after everything succeeded. On any error an existing output file keeps its old contents and a pipe receives nothing, so the next tool fails on an empty input instead of converting half a dictionary. The target is checked when it is opened (folder exists, file or folder writable), so a wrong path fails before the work. Only an I/O error during the final write itself (e.g. a full disk) can leave a partial file.

Messages, errors and exit codes

  • Data goes to stdout only through SafeOutput; everything people read (listing, progress, warnings, errors) goes to stderr as tool: message (ToolLog), so pipes carry data only.
  • ToolRunner is the only place that ends a program: normal end → 0; help → 0; a usage or input error (CliException) → its message (and the usage, if useful) and 1; a file error such as a read-only or missing file → one line, e.g. tool: Error: out.dic: permission denied, and 1; any other exception is a bug → message and stack trace, 1.

kaikki-2-tab
Kaikki JSONL Wiktionary extractor — .jsonl / .jsonl.gz → TSV
java/ConvKaikki2Tab.java · class ConvKaikki2Tab · run by linux/kaikki-2-tab

Overview

kaikki-2-tab reads the Kaikki.org JSONL data (Wiktionary extracted to one JSON object per line and headword) and writes a TSV for tab-2-xdxf. It keeps the entries of one headword language and builds an HTML definition for each, with labels translated into the definitions' language.

Requirements

InputKaikki .jsonl or .jsonl.gz (by extension)
OutputUTF-8 TSV: word⇥HTML definition, one entry per line; file or stdout
Label translationsjava/term-translations_<lang>.properties by default, or --terms-file
Config namespacekaikki2tab.*

CLI Interface

kaikki-2-tab -i <jsonl[.gz]> -o <tsv|-> -l <lang>
             [-e / --embedded-defs KEEP|SEPARATE|BOTH] [--terms-file <file>]
             [-c <config>] [--def <name>=<value> ...]

Design Choices

Language filtering

-l takes one ISO 639-1 code; lines whose lang_code differs are skipped first, before the rest of the entry is used. The count of skipped lines and their languages is logged.

Definition structure

buildDefinition() builds the HTML in a fixed order: part of speech and gender (bold title); plural forms (nouns only); pronunciation; numbered senses with domain labels (from topics, else raw_tags) and usage examples; etymology; expressions. Form-of entries (conjugations, plurals) get a short definition; verbs do not list their conjugated forms; entries without senses are skipped.

Expressions — --embedded-defs

  • BOTH (default) — expressions appear inside the parent entry and also as their own entries, for direct lookup.
  • KEEP — only inside the parent entry.
  • SEPARATE — only as their own entries. An expression is not emitted on its own when a regular entry with the same headword exists.

Label translations

Labels such as Etymology, feminine or domain topics (Botany) are translated with a .properties file (english-term=translation, case-insensitive). The file used is logged; a missing default file leaves the labels in English. For dictionaries whose definitions are in another language than the headwords, --terms-file should point to the definitions' language (as confs/kaikki2xdxf-en-pt.config does).

Wiki markup and TSV safety

stripWiki() resolves [[word]] and [[word|display]] links and removes stray brackets; sanitize() collapses embedded newlines and tabs so every entry stays one TSV line.

Duplicates and errors

Identical lines (same headword and definition) are written once: SeenLines keeps a 128-bit hash of each line instead of the line itself, to save memory. A malformed JSON line is reported with its line number and skipped; any other error stops the run.

Program Structure — ConvKaikki2Tab

  • run() — options, config, stream loop over the lines, output, statistics
  • EmbeddedDefs — the -e modes as an enum (embedded, separate)
  • buildDefinition() · prepareExpressionsToEmit() — HTML definition of an entry; its expressions as separate entries
  • extractGloss() · buildExampleText() · buildSoundsMap() · buildDomainText() — parts of a definition
  • loadTermTranslations() · translateTerm() — label translations (TermTranslator)
  • stripWiki() · sanitize() — wiki links, TSV safety
  • SeenLines — hashed set of the lines written

StarDict dictionary reader — .ifo / .idx / .dict[.dz] → TSV

Overview

stardict-2-tab reads a StarDict dictionary (.ifo + .idx + .dict.dz or .dict) and writes a TSV with one entry per line for tab-2-xdxf.

Requirements

Implemented byjava/ConvStardict2Tab.java (class ConvStardict2Tab), launched by linux/stardict-2-tab
InputStarDict .ifo; the .idx and .dict.dz (or .dict) with the same name in the same folder

Config namespacestardict2tab.*

CLI Interface

stardict-2-tab -i <input.ifo> -o <tsv|-> [-c <config>] [--def <name>=<value> ...]

Design Choices

Sidecar file discovery

The .idx and dictionary files are found from the .ifo path; .dict.dz is preferred when both exist. A missing file is reported by name.

Strict .ifo check

The first line must be StarDict's dict ifo file; anything else is a clear error (CliException) instead of a confusing failure later.

Reading by index

The .idx is read as word\0 + 4-byte offset + 4-byte size (big-endian). For a .dict.dz, only the bytes the index refers to are decompressed, straight into one array of that size, and the rest of the stream is read so the gzip checksum is still verified; a truncated file is reported.

TSV line normalisation

Newlines and tabs inside definitions become spaces, so each entry is exactly one line with one tab. HTML is kept as is for tab-2-xdxf.

Program Structure — ConvStardict2Tab

  • run() — options, config, read, write the TSV through SafeOutput
  • readStarDict() — parses the .ifo, reads the .idx into RawEntrys, decompresses the dictionary and resolves the definitions
  • RawEntry (word, offset, size) · Entry (word, definition) — records
tab-2-xdxf
TSV to XDXF converter — produces validated XML
java/ConvTab2Xdxf.java · class ConvTab2Xdxf · run by linux/tab-2-xdxf

Overview

tab-2-xdxf reads a TSV dictionary (from kaikki-2-tab or stardict-2-tab) and writes a well-formed XDXF file, the common input of xdxf-2-pbdic and xdxf-2-stardict. It cleans the HTML definitions and validates the result with Java's SAX parser.

Requirements

Implemented byjava/ConvTab2Xdxf.java (class ConvTab2Xdxf), launched by linux/tab-2-xdxf
InputUTF-8 TSV word⇥HTML definition, file or stdin; blank lines and lines starting with # are ignored, lines without a tab are reported and skipped
OutputUTF-8 XDXF, one <ar> per entry; file or stdout
ValidationSAX parse of the output before it is written (default on)
Config namespacetab2xdxf.*

CLI Interface

tab-2-xdxf -i <tsv|-> -o <xdxf|-> -l <lang> -n <name>
           [-t / --lang-to <lang>] [--desc <text>] [-v / --validate true|false]
           [-c <config>] [--def <name>=<value> ...]

Design Choices

HTML cleaning (XmlHelper.cleanHtml)

  • Only whitelisted tags are kept, without attributes: p b i u em strong big small ol ul li sub sup br a div span table tr td th; other tags are dropped, keeping their text.
  • Void elements (br, hr, img) are self-closed; unbalanced tags are fixed.
  • Common HTML entities become characters; bare & and < are escaped.

Language codes

XDXF needs three-letter codes in lang_from / lang_to; LangHelper maps the ISO 639-1 codes given with -l and -t (default: the headword language).

Validation without temporary files

The XDXF is written entry by entry into a SafeOutput (no list of entries in memory). With validation on, the compressed in-memory output is read back and parsed; only if it is valid is it written to the file or stdout. On failure nothing is written and the tool exits with 1. This works the same for a file and for stdout.

Program Structure — ConvTab2Xdxf

  • run() — options, config, the XDXF header, write, validate, commit
  • readTabfile() — TSV reader feeding the XDXF writer line by line
  • XdxfHelper.openXdxfWriter / XdxfWriter — XDXF header, <ar> entries (cleaned HTML), footer
  • XdxfHelper.validateXdxf — SAX well-formedness check
xdxf-2-pbdic
XDXF to PocketBook SDIC converter — produces native .dic files
java/ConvXdxf2Pbdic.java · class ConvXdxf2Pbdic · run by linux/xdxf-2-pbdic

Overview

xdxf-2-pbdic reads an XDXF dictionary and writes a PocketBook-native .dic: a sorted, indexed binary with the collation table, the morpheme and keyboard language data, a word index and zlib-compressed definition blocks. The binary format is described in docs/sdic_format.pdf.

InputXDXF file or stdin
OutputPocketBook .dic (SDIC)

Required--in, --out, --lang, --merge-defs
Config namespacexdxf2pbdic.*

CLI Interface

xdxf-2-pbdic -i <xdxf|-> -o <dic> -l <lang> -m ALWAYS|EXACT|NEVER
             [-D / --langdir <dir>] [-n / --name <title>]
             [-c <config>] [--def <name>=<value> ...]

Processing steps

  1. Language files — collation map, morphemes (UTF-16 LE, uppercased), keyboard (verbatim).
  2. Parse XDXF — SAX; each definition is converted to SDIC bytes (htmlToSdic); an <ar> with several <k> gives one entry per headword; entries with an empty definition are skipped. The title comes from -n, else the XDXF header, else the file name.
  3. Oversized definitions — a definition that does not fit in one block on its own is cut and ends with [...].
  4. Sort — by collation key, then lowercase word, then word.
  5. Merge — repeated definitions dropped, then duplicate headwords merged according to -m.
  6. Pack into blocks, build the index, write the file.

Design Choices

--merge-defs (mandatory)

There is no default, forcing an explicit choice (MergeMode):

  • ALWAYS — headwords that differ only in case are the same headword; different definitions are joined into one entry, separated by a blank line (0x0A 0x20 0x0A).
  • EXACT — case-sensitive headword match; different definitions of the exact same headword are joined.
  • NEVER — nothing is joined.

In every mode, a definition repeated for the same headword is kept only once, wherever its copies are. With ALWAYS the joined entry is named after its most common spelling: a common word before a name before an acronym (TextHelper.wordKind, by spelling only), then fewer capitals — Fausta + fausta → fausta; a repeated definition of an acronym keeps its capitals (FUNASA + funasa → FUNASA).

Block size limits

An entry must fit in one block, whose decompressed size is limited by the firmware's buffer:

  • A single definition too large on its own is cut at a newline or a space, never inside a word or a bold/italic span, and ends with [...]; it is logged as a warning.
  • A join whose result would not fit is not done: the definition stays a separate entry with the same headword, and the following definitions join that one if they fit. Nothing is cut because of a join; it is logged as a note.

Block packing

TARGET_BLOCK_COMPRESSED   = 4_096   // compressed size, as converter.exe
TARGET_BLOCK_DECOMPRESSED = 27_000  // hard ceiling on the decompressed size (firmware buffer)
TARGET_BLOCK_ENTRIES      = 110     // entries per block: keeps the index under ~55,000 bytes

A block is closed before the entry that would break one of its limits: more than 110 entries, more than 27,000 bytes decompressed (with the 2-byte terminator), or — once over 3,000 bytes — more than 4,096 bytes compressed. The compressed size is measured only when it could be over the limit (maxDeflateGrowth bounds how much it can grow per added byte), with one reused Deflater; the blocks are the same as when measuring after every entry, only faster.

SDIC definition encoding rules

The firmware requires strict spacing around the format bytes (0x02 bold, 0x03 italic, 0x01 end of span, 0x0A newline); a post-processing pass enforces them on every definition:

  • a definition starts and ends with 0x20;
  • 0x01 is followed by 0x20; 0x0A is preceded by 0x20 and followed by exactly one;
  • 0x02 and 0x03 are preceded and followed by 0x20.

Collation table

collates.txt is parsed into a map from source code point to normalised code point; its first line lists the ignored characters (mapped to 0), the following lines are chars=BASE. The map drives the sort order and is written to the .dic uncompressed: a uint32 byte count, then one little-endian uint32 per pair (source code point in the low half, normalised one in the high half), sorted by source; identity mappings are left out.

Program Structure — ConvXdxf2Pbdic

  • run() — options, config, the steps above, output through SafeOutput
  • loadCollation() · collatedKey() · sortByCollatedKey() · collationToBytes() — collation
  • htmlToSdic() · trimBytes() — HTML to SDIC bytes, spacing rules
  • maxDefinitionBytes() · truncateOversized() · truncateDefinition() — the block-size rule for one definition
  • joinDefsBlankLine() — joins two definitions; MergeMode.dropRepeated() / decide() / keptWord() drive the merge
  • packBlocks() · PendingBlock · maxDeflateGrowth() — block packer
  • buildIndex() · writeDic() — index (with its 0x0000 terminator) and the file
  • readAsUtf16Le() — morphemes block
xdxf-2-stardict
XDXF to StarDict converter — for KOReader and other StarDict readers
java/ConvXdxf2Stardict.java · class ConvXdxf2Stardict · run by linux/xdxf-2-stardict

Overview

xdxf-2-stardict reads an XDXF dictionary and writes a StarDict dictionary into a folder: stardict.ifo, stardict.idx and stardict.dict.dz (or an uncompressed stardict.dict). Definitions are stored as HTML (sametypesequence=h), keeping the markup made by tab-2-xdxf.

Requirements

Implemented byjava/ConvXdxf2Stardict.java (class ConvXdxf2Stardict), launched by linux/xdxf-2-stardict
InputXDXF file or stdin
OutputA folder (created if missing) receiving the stardict.* files
Required--in, --out, --merge-defs, --compress
Config namespacexdxf2stardict.*

CLI Interface

xdxf-2-stardict -i <xdxf|-> -o <dir> -m ALWAYS|EXACT|NEVER -z true|false
                [-n / --name <title>] [-c <config>] [--def <name>=<value> ...]

Design Choices

Merging

Same -m modes and rules as xdxf-2-pbdic (MergeMode): repeated definitions dropped, case variants sorted together (by lowercase word, then word), the ALWAYS name chosen by wordKind. Joined definitions are separated by <hr/>. StarDict has no block-size limit, so nothing is cut and every join is done.

Replacing a previous build safely

  • Before any work, the folder and its stardict.* files must be writable; a read-only file was protected on purpose, so the tool stops and leaves the previous build unchanged.
  • The size is checked before any file is touched: 4 GB for .dict (32-bit offsets), about 1.9 GB for .dict.dz.
  • The .idx and dictionary are built in memory, compressed; only when everything is built are the old stardict.* files (including a stale .syn) removed and the new ones written, the .ifo last. Other files in the folder are never touched.

Dictzip

DictzipHelper writes .dict.dz as one deflate stream with a full flush at each chunk boundary and the chunk sizes in the gzip header (RA field), so readers can seek to any entry; the file is also a plain gzip file.

Program Structure — ConvXdxf2Stardict

  • run() — options, config, parse, sort, merge, size check, write
  • checkReplaceable() · checkDictSize() — checks before any work / before touching files
  • writeStardict() — builds .idx (word\0 + big-endian offset + size) and .dict[.dz], then .ifo
  • joinDefs() — joins two definitions with <hr/>
check-pbdic
PocketBook .dic validator — cross-checks the binary against its XDXF
java/CheckPbdic.java · class CheckPbdic · run by linux/check-pbdic

Overview

check-pbdic is a testing tool: given the source XDXF and the .dic made from it, it runs a series of checks and reports each as PASS, FAIL or WARN, with a summary at the end.

Requirements

Implemented byjava/CheckPbdic.java (class CheckPbdic), launched by linux/check-pbdic
InputSource XDXF + .dic + language folder (collates.txt)
OutputReport to stderr; exit code 0 when all checks passed, 1 otherwise
Config namespacecheckpbdic.*

CLI Interface

check-pbdic -x <source.xdxf> -d <file.dic> -l <lang>
            [-s / --sample <count>] [-D / --langdir <dir>]
            [-c <config>] [--def <name>=<value> ...]

Checks Performed

  • Entry count — entries in the .dic against the XDXF
  • Headwords — every XDXF headword present in the .dic
  • Sort order — .dic entries in collation key order
  • Definitions — N sampled entries (default 20) have the XDXF's text
  • Firmware format — spacing rules around the format bytes
  • Block sizes — compressed ≤ 4,096 bytes; decompressed ≤ 27,774 bytes; index ≤ 55,000 bytes
With -m ALWAYS or EXACT, merging makes the entry count lower than the XDXF's, and a headword merged into another spelling is reported as missing: those failures are expected and show how much was merged.

Design Choices

Independent binary reader

The .dic reader (parseDic()) is written separately from xdxf-2-pbdic: it parses the header, decompresses the index and every definition block from the format description, so it can find writer bugs that a shared reader would hide. The collation code is duplicated for the same reason.

Definition text comparison

The spot-check turns the SDIC bytes back into plain text (format bytes removed) and compares it with the XDXF definition's text (tags removed), with whitespace normalised.

Program Structure — CheckPbdic

  • run() — options, loading, the checks, summary and exit code
  • parseDic() · parseXdxf() — readers
  • loadCollation() · collatedKey() — collation, as in xdxf-2-pbdic
  • stripFmt() · htmlToText() — text for the comparison
  • pass() · fail() · warn() — report

Design Choices

  • One config, several tools: every step gets the same config file (each tool reads its own namespace) and the same --def arguments; ready-made configs are in confs/.
  • Runs from anywhere: the config's relative paths are taken from the project root.
  • Temporary TSV: the first step writes a temporary TSV, removed when the script ends, so a failure never overwrites the final output; the script stops at the first failing step and shows [n/N] step messages.
  • Shared code: linux/library.sh holds the argument handling, the move to the project root, the config section check, the temporary TSV and the step messages; a chain script only sets its name and number of steps and lists its tool calls.
