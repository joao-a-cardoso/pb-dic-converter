PocketBook SDIC Format

Reverse Engineering Report & Converter Implementation Notes

Binary format analysis of PocketBook's native .dic dictionary format, derived from converter.exe output paired with known XDXF source files and the LanguageFilesPocketbookConverter language files (collates.txt, morphems.txt, keyboard.txt), and confirmed by the open-source converter xdxf-2-pbdic (java/ConvXdxf2Pbdic.java) on a PocketBook InkPad.

March 2026 — revised November 2026 to match the current implementation

1. Overview

The PocketBook .dic format is a proprietary binary dictionary format consumed by PocketBook e-reader firmware. Conversion from XDXF was originally only possible with a closed-source Windows tool (converter.exe) distributed on the MobileRead forums. This report documents the binary layout of the format, reverse-engineered from known XDXF/DIC file pairs, as implemented in xdxf-2-pbdic.

The format identifier is the four-byte magic string SDIC at the start of every file. Definitions use a compact binary markup with single-byte control codes (0x01–0x03, 0x0A) for bold, italic and newlines. Every definition begins and ends with a space byte (0x20).

2. File Layout

A .dic file consists of a fixed 128-byte header followed by contiguous sections. The collation table is stored uncompressed. The morphem, keyboard and index blocks are each a 4-byte little-endian decompressed size followed by zlib-compressed data. Definition blocks are raw zlib streams only — they have no size prefix.

4. Collation Table

The collation table drives case-insensitive and accent-insensitive search. It is stored uncompressed immediately after the header at offset 0x80: a uint32 byte count, then one little-endian uint32 per mapping, holding the source code point in its low half and the normalised code point in its high half — that is, a uint16 pair (source, normalised) in byte order. Pairs are sorted by source code point. A normalised value of 0x0000 means the character is ignored (punctuation, whitespace). Identity mappings (a character mapped to itself) are not written; any code point absent from the table is its own normalised form. Only code points up to 0xFFFF can be stored.

The Portuguese table has 395 pairs (1,580 bytes after the count). It is derived from collates.txt in the language folder: the first line lists the ignored characters; each following line is chars=BASE.

# collates.txt line:          # resulting binary (after the uint32 byte count):
aáàâãä...=A                    61 00 41 00   (a → A)
                               E1 00 41 00   (á → A) ...
# first line, ignored characters (→ 0x0000):
.,-_ '`!?:;...                 2E 00 00 00   (. → ignored)
                               21 00 00 00   (! → ignored)

5. Compressed Block Format

The morphem, keyboard and word index blocks share a common container format:

uint32_le  decompressed_size   // size of the data after decompression
byte[]     zlib_data           // standard zlib (deflate) stream

Definition blocks do not use this format. They are raw zlib streams with no size prefix. The compressed size of each def block is obtained from the word index; the decompressed size is not stored anywhere and follows from the zlib stream itself.

6. Morphem Block

The decompressed content of the morphem block is the content of morphems.txt (UTF-8, a byte-order mark removed), uppercased and encoded in UTF-16 LE (2 bytes per character). Empty lines are dropped; each line is followed by a uint16 NUL (0x0000), and the block ends with one more uint16 NUL (a double NUL after the last line). It holds inflection-stripping rules that let the firmware find the base form of an inflected word (e.g. running → run); they are interpreted by the firmware at lookup time.

7. Keyboard Block

The decompressed content of the keyboard block is the verbatim content of keyboard.txt (UTF-8). It defines the layout of the on-screen keyboard used to type a word to look up; it is embedded as is and interpreted by the firmware.

8. Word Index Block

The word index is a sparse index: one entry per definition block, with the compressed size of that block and its first headword. The firmware uses binary search on it to find the right def block without decompressing all blocks. Each entry in the decompressed index stream:

uint16_le  compressed_size     // compressed byte size of the corresponding def block
byte[]     word\0              // UTF-8 NUL-terminated first headword of that block

Entries are contiguous with no padding. Index entry N corresponds to def block N (def block 0 is at defblocks_offset). The index ends with a uint16 0x0000 terminator, as in converter.exe output; without it the firmware reads past the end of the index into adjacent memory, causing crashes when several dictionaries are loaded.

Firmware index size limit: the decompressed index must stay below about 55,000 bytes — exceeding it makes the firmware hang on dictionary load. This limits the number of def blocks; xdxf-2-pbdic puts at most 110 entries in a block, which keeps the index at about 50,000 bytes for a dictionary of about 384,000 entries (Kaikki 2026-11.1 PT→PT: 50,155 bytes).

9. Definition Blocks

Definition blocks are the bulk of the file. Each block is a raw zlib stream with no size prefix; its compressed size comes from the word index. Each block decompresses to a sequence of dictionary entries followed by a two-byte NUL terminator. Each entry:

uint16_le  entry_length        // total byte length of this entry (including this uint16)
byte[]     word\0              // UTF-8 NUL-terminated headword
byte[]     definition\0        // UTF-8 NUL-terminated definition (see §10 for encoding)

// End of block — mandatory 2-byte terminator:
uint16_le  0x0000              // signals end of block to firmware

entry_length counts the bytes from the start of the uint16 to the end of the definition's NUL terminator, inclusive, which allows forward scanning without parsing the definition. Entries are sorted by collation key across all blocks.

Every def block must end with a 0x0000 uint16 after the last entry. Without this terminator the firmware reads past the last entry into garbage bytes and hangs.
Firmware decompression buffer limit: a block must decompress to at most about 27,774 bytes (the largest observed in converter.exe output). Exceeding this overflows the firmware's fixed decompression buffer and crashes it. This limit is independent of — and, for highly compressible text, stricter than — the compressed size of 4,096 bytes.

xdxf-2-pbdic therefore closes a block before the entry that would break one of three limits: 110 entries, 27,000 bytes decompressed (terminator included), or — once the block holds more than 3,000 bytes — 4,096 bytes compressed, as converter.exe. Because one entry must fit in one block, a definition larger than a block on its own is cut at a newline or a space (never inside a word or a bold/italic span) and ends with [...], and definitions of duplicate headwords are joined only when the result still fits (see the design reference).

10. Inline Formatting Codes

Definition text uses single-byte control codes for text styles, inline within the UTF-8 definition. Every definition must begin with a space byte (0x20) — the firmware requires it.

ByteMeaningHTML equivalentExample context
0x20Leading / trailing space (required)—First and last byte of every definition
0x01End format span</b> or </i>After bold/italic text
0x02Begin bold<b>Part of speech: Substantivo, Verbo…
0x03Begin italic<i>Gender markers, cross-references, labels
0x0ANewline<br/> / end of <p>, <div>, <li>Between senses, after the POS line
0x00NUL terminator—Ends the word and definition fields

Spans do not nest: a 0x01 always closes the open span. List items start with a bullet • (U+2022, encoded 0xE2 0x80 0xA2) followed by a space, written by xdxf-2-pbdic for each <li>; <ol> and <ul> produce nothing themselves. Other tags are dropped, keeping their text; HTML entities are decoded; literal newlines in the XDXF text are ignored. Joined definitions of a duplicate headword are separated by a blank line, 0x0A 0x20 0x0A.

Firmware spacing rules — all must hold or the firmware may crash: (1) every definition starts with 0x20; (2) every definition ends with 0x20; (3) every 0x01 is followed by 0x20; (4) every 0x0A is preceded by 0x20. xdxf-2-pbdic enforces them in a post-processing pass on every definition, and also writes 0x02 / 0x03 followed by 0x20 and exactly one 0x20 after each 0x0A.

11. Converter Implementation

The converter is xdxf-2-pbdic, a Java 25 source program (java/ConvXdxf2Pbdic.java, run by linux/xdxf-2-pbdic) in the same style as the rest of the toolchain. Input: an XDXF file (or stdin), a language code and a merge mode (-m ALWAYS|EXACT|NEVER). Output: a .dic file, written only when everything succeeded. Language files are read from lang/<lang>/, or the folder given with -D. Options and design choices are described in docs/toolchain-design-reference.pdf.

Phase 1 — Language Files

collates.txt is parsed into a map of code point → normalised code point; morphems.txt is uppercased and re-encoded as UTF-16 LE (§6); keyboard.txt is read as raw UTF-8 bytes.

Phase 2 — Parse XDXF

A SAX parser streams the entries; each definition's HTML is converted to the inline codes of §10. An <ar> with several <k> headwords gives one entry per headword; entries with an empty definition are skipped. A definition too large for one block is cut and ends with [...].

Phase 3 — Sort and Merge

Entries are sorted by collation key (each headword mapped through the collation table, ignored characters skipped), then by lowercase word, then by word. A definition repeated for the same headword is kept once. Duplicate headwords are then handled by the merge mode: ALWAYS treats headwords that differ only in case as one and joins different definitions; EXACT joins different definitions of the exact same headword; NEVER joins nothing.

Phase 4 — Pack into Blocks

Entries are serialised (uint16 len | word\0 | def\0) into blocks with the three limits of §9; each block gets its 0x0000 terminator and is compressed with zlib. No uint32 decompressed size is prepended — def blocks are raw zlib only.

Phase 5 — Build Word Index

One index entry per def block: uint16 compressed_size | first_word\0, then the 0x0000 terminator; the whole index is compressed and prefixed with its uint32 decompressed size.

Phase 6 — Build Collation Table

The uint32 byte count, then the non-identity pairs as little-endian uint32 values sorted by source code point (§4). This section is not compressed.

Phase 7 — Write Header and Assemble File

Compute all section offsets, write the 128-byte header, then concatenate the sections in order:

header          (128 bytes, fixed)
collation table (uint32 byte count + uint32 pairs, no compression)
morphem block   (uint32 dsz + zlib)
keyboard block  (uint32 dsz + zlib)
word index      (uint32 dsz + zlib)
def block 0     (raw zlib — no size prefix)
def block 1     (raw zlib — no size prefix)
...
def block N-1   (raw zlib — no size prefix)
